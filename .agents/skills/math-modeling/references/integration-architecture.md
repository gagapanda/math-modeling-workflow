# 融合架构说明

## 目标

让新手可以从一句题目描述进入正确的建模阶段，同时让所有实际执行仍经过现有的证据链和质量门：

`任务识别 -> 问题契约 -> 数据审计 -> 模型路由 -> 基线/主模型 -> 验证 -> 论文与提交审计`

## 分层

### 入口层

负责识别用户意图和缺失输入：学习、历史题练习、论文审查、业务分析或正式竞赛。入口层只做路由，不运行模型，也不声称结果。

### 建模层

复用现有 problem-definition、model-definition-gate、model-routing 和 references。出售版的拆题、变量、假设和模型卡在这一层提供更友好的表格化输出。

### 执行层

由现有 workflow manifest、Python/MATLAB steps、输入输出路径、缓存和 preflight 负责。新脚本必须作为显式 step 或经过审计的 helper 接入。

### 证据层

由 diagnostics、结果对账、模型定义审计、视觉审查、submission compliance 和 hash 绑定记录负责。任何短脚本都不能绕过这一层。

## 路由输出契约

题型路由必须输出：

1. 任务模式；
2. 题型判断及证据；
3. 需要补充的最少信息；
4. 透明基线；
5. 候选主模型和备选模型；
6. 每个候选模型的失败模式；
7. 与题型匹配的验证方法；
8. 下一步应调用的 reference、脚本或 workflow 阶段。

如果缺少目标、约束、数据口径或时间/空间尺度，路由层只能列出缺口，不能直接选复杂模型。

## 依赖原则

- 主流程依赖保持最小；`scikit-learn` 只在分类、聚类和机器学习回归需要时加载；
- 求解器依赖必须在 manifest/preflight 中显式声明；
- Windows 命令使用当前解释器绝对路径或项目 `.venv`，不使用裸 `python3`；
- 所有临时输出写入系统临时目录或 case 内声明目录，不写硬编码 `/tmp`；
- 原始输入只读，处理数据和报告写到独立输出目录。

## 不变量

融合后必须继续满足：

- 所有结果可追溯到输入、代码和参数；
- 至少有一个透明基线；
- 数值结论有匹配的验证；
- 重大定义歧义先登记并比较；
- 论文、图表和结果模板来自同一权威结果；
- 完成质量门前不称为提交就绪。
